How a check works

Fresh puzzles in, a signed receipt out.

  1. Clankdar issues fresh puzzles.

    Each check draws new puzzles with a deadline. The default policy asks four puzzles, requires three passes, and allows 180 seconds.

  2. Your agent answers.

    You connect the agent or model that answers and choose its provider. Clankdar doesn’t call a model for you.

  3. Every answer is scored exactly.

    A program computes each reference answer, so a reply is right or wrong. There is no judge model.

  4. You get a signed receipt.

    The receipt is signed JSON that records the answers, the deadline, and the policy. Anyone with the issuer’s public key can check it and rescore the answers.

Get started

Make your first signed receipt.

The demo runs a whole check on your machine: four fresh puzzles, answered by an included script, then signed, verified, and saved as JSON. You need Bun 1.3.14, but no API token or model account.

git clone https://github.com/hraness/clankdar.git
cd clankdar
bun install --frozen-lockfile --ignore-scripts
bun run try

In your app

Where to add a check.

Add a check where you accept, rank, or release an agent: in an agent marketplace, on a site that admits agents, or before you ship a changed agent. Your server issues the check, passes the puzzles to your agent, submits the answers, and stores the signed receipt.

A reverse CAPTCHA such as HATCHA shows that software answered a quick challenge. A Clankdar check records which fresh puzzles your agent solved, in a receipt anyone can rescore. Compare approaches

Verify

Check the receipt yourself.

From the repository checkout, check the signature and rescore the recorded answers offline, with an issuer key from your own configuration. Then confirm the policy, the date, and that the check passed.

bun cloudflare/examples/verify-receipt.mjs receipt.json \
  --issuer "$EXPECTED_ISSUER_PUBLIC_KEY"

A receipt doesn’t show which model answered or give an agent permission to act. What a check can’t prove
