Run a complete check.

Want to see a puzzle first? Try browser practice without an install or signup. For a real signed receipt, install Bun 1.3.14 and run:

git clone https://github.com/hraness/clankdar.git
cd clankdar
bun install --frozen-lockfile --ignore-scripts
bun run try

The demo creates four fresh Algal puzzles, solves them with an included script, and signs and independently verifies the result. It saves receipt.json and verification.json in a new results/try-…/ directory and prints the paths and verification command.

No credentials or model calls are involved. The local signing key is temporary, and the scripted score is a flow check, not a model score or hosted attestation.

Use your own solver

Export solve(challenges, signal) from a JavaScript or TypeScript module, then run:

bun run try --solver ./my-solver.mjs

Your function receives public challenge objects and an AbortSignal. Return an object mapping each actual challengeId to its answer string. For example, connect your existing agent in my-solver.mjs:

import { askAgent } from "./your-agent.mjs";

export async function solve(challenges, signal) {
  const answers = {};
  for (const challenge of challenges) {
    answers[challenge.challengeId] = await askAgent(challenge.prompt, { signal });
  }
  return answers;
}

askAgent is your application function, not a Clankdar API. Return only each requested answer, forward the signal to provider requests, and set your own model and spending bounds. Loading your module runs its code and can incur your provider costs. The default policy requires three of four correct answers within 180 seconds.

Use the API from your server.

The hosted API is invitation-only experimental staging. Request hosted access, then store your token privately as CLANKDAR_TOKEN. No agent registration or campaign setup is required.

Use ordinary HTTP, or download the small JavaScript helper. It runs on Node 22+ or Bun and needs no repository checkout:

curl -fsS https://clankdar.com/clankdar-client.mjs -o clankdar-client.mjs

Connect the same solve function from the local example in your server code:

import { writeFile } from "node:fs/promises";
import { check } from "./clankdar-client.mjs";
import { solve } from "./my-solver.mjs";

const result = await check({
  baseUrl: "https://clankdar-hosted-staging.972abc65.workers.dev",
  token: process.env.CLANKDAR_TOKEN,
  solve,
});
await writeFile("receipt.json", result.receiptText);
console.log(result.receiptUrl);

The helper issues a check, passes its prompts to your solver, submits the answers, and downloads the exact receipt bytes. Your solver chooses any provider and pays its own compute costs. Keep the token and live ticket off the browser; submitted answers and optional context become public evidence.

Verify the receipt before relying on it. The helper’s download and hash check do not establish a trusted issuer or a passing result.

Recover a submission after a connection failure

The first accepted submission fixes the result, even when it fails. Retry that submission to recover the result; creating another check consumes another quota slot. Use the helper’s optional onIssued(record) and checkpoint(record) callbacks to save the ticket privately before solving and the answers before submitting. The helper source and API contract describe the records and retry behavior.

Verify before you rely on a result.

From the repository checkout, use the offline verifier with an issuer key from your trusted application configuration:

bun cloudflare/examples/verify-receipt.mjs receipt.json \
  --issuer "$EXPECTED_ISSUER_PUBLIC_KEY"

The checker verifies the signature and replays the recorded answers. Your app must require its expected policy, suitable freshness, and a passing result. A valid receipt can record a failed check. For the local demo, use the exact verification command printed by bun run try.

Signer pins, expected context, and replay details

Never take the expected issuer key from the receipt you are checking. Optional --context, --session, and --sha256 assert your integration’s expected context, check ID, and exact file hash. See the verifier source for its output.

Present, well-formed answers produce challenge receipts with seeds that let a checker regenerate and rescore those puzzles. Missing or malformed answers count as nonpassing without a challenge receipt or seed reveal. An empty-answer control still independently verifies as zero of four passing.

Three HTTP calls.

POST /v1/checks
Send {} with your bearer token. Receive fresh challenges, their deadline, a scoped ticket, and the future receipt URL.
POST /v1/checks/:id/responses
Send {"ticket":"…","responses":{"actualChallengeId":"answer"}}. Receive the score, signed receipt, URL, and exact-byte hash. No issue token is needed.
GET /v1/checks/:id
Download the immutable canonical JSON receipt. This read needs no token.

The default algal-floor-v1 policy asks four puzzles, requires three passes, and allows 180 seconds. Every answer is checked exactly; there is no judge model.

Policy selection and optional fields

Set policyId when issuing to choose v2-floor-v1 (120 seconds) or frontier-floor-v1 (180 seconds). Each asks four puzzles and requires three passes. These settings are not certified model classes. List hosted policies.

Optional context is a nonempty, non-sensitive string up to 256 characters. It becomes part of the public result.

Bind a check to a subject key

Include subjectPublicKey when issuing and the matching subjectProof when submitting. This binds a key to the check, not the identity of its solver. Most integrations can start without it. The API contract defines the proof format.

Exercise the HTTP flow with curl and jq

This optional control uses a hosted invitation token and a quota slot. It submits blank answers for a deliberately failed result; it does not call a model.

Create a check and inspect its prompts.

export CLANKDAR_URL="https://clankdar-hosted-staging.972abc65.workers.dev"
# Set CLANKDAR_TOKEN privately to your invitation token.
umask 077
curl -fsS "$CLANKDAR_URL/v1/checks" \
  -H "Authorization: Bearer $CLANKDAR_TOKEN" \
  -H "Content-Type: application/json" \
  --data '{"policyId":"algal-floor-v1"}' > check.json
jq -r '.challenges[] | "\(.challengeId)\n\(.prompt)\n"' check.json

check.json contains the actual challenge IDs and prompts, expiresAt, and a private ticket for this check. The default algal-floor-v1 policy gives you four Algal program puzzles, requires three passing answers, and allows 180 seconds. Creating the check does not call a model.

Build the answer map and submit once.

jq '.challenges | map({key: .challengeId, value: ""}) | from_entries' \
  check.json > answers.json

This creates blank answers under the real challenge IDs. Submit them unchanged for an intentionally failed-check demo. To test capability, replace each blank value with your solver’s answer before expiresAt. No model is called by these commands. Failed answers consume the attempt just as passing answers do.

jq -n --slurpfile check check.json --slurpfile answers answers.json \
  '{ticket: $check[0].ticket, responses: $answers[0]}' > submission.json
curl -fsS "$CLANKDAR_URL/v1/checks/$(jq -r '.id' check.json)/responses" \
  -H "Content-Type: application/json" \
  --data-binary @submission.json > result.json
jq '{id, pass, passed, required, receiptUrl, sha256}' result.json

The response includes pass, the passing and required counts, a content hash, a receipt URL, and the signed receipt itself. Submission uses the scoped ticket, so your main issue token stays with your server. Retrying submission recovers the first result; it cannot replace the answers. Retrying creation makes a new check and consumes another quota slot.

Download the exact JSON receipt.

curl -fsS "$CLANKDAR_URL$(jq -r '.receiptUrl' result.json)" > receipt.json

The receipt is a raw clankdar-gate-v1 signed admission with protocol, payload, and signature. It remains readable after the ticket expires. Keep a copy: this experimental service has no automatic deletion policy, but does not promise permanent hosting.

How Clankdar uses Algal

Algal supplies the language. Clankdar supplies the check.

The new clankdar-algal-v1 suite presents real algal.expr.v1 programs and fresh inputs. Algal’s official Rust evaluator, compiled to WebAssembly, calculates the reference answer. The CLI and Worker use the same pinned evaluator; Clankdar adds deadlines, exact response scoring, and signed receipts.

Programs compose filtering and arithmetic, coupled recurrences, and matrix transitions. They have a 10,000-unit work budget and no network, filesystem, or model access. Your solver returns only the final integer. Clankdar does not execute code supplied in a response.

bun run algal:example
bun bench --suite algal --adapter oracle --seeds 1-10 --out results/algal-control.jsonl

These local commands need a repository checkout, Bun 1.3.14, and installed dependencies. They make no model calls; the oracle is a runner control. Inspect the program contract, evaluator pin, and worked example.

The Algal suite has no model calibration yet. Published v2/frontier results remain attached to their original suites, and older receipts still replay. A tier describes program structure, not a certified capability level.

Tiers mix different families, so they are not one intelligence number. Inspect the capability profiles, counts, exclusions, and uncertainty before choosing your own evaluation conditions.

Keep evaluation tracks separate.

Frontier measures harder unaided tasks; the tool-agent suite records bounded tool episodes. Those tracks do not share a leaderboard. Four published signed reference sessions contain 32 challenge checks, all replayed by the site build. Explore the benchmark and downloadable evidence.

Other systems use puzzles too. Clankdar’s distinction is inspectable task evidence. Public tasks can be solved with code or delegated; results do not establish model identity or human presence.

Limits, storage, and boundaries.

Shared staging allows 1,024 issued checks over its lifetime and at most 60 issues per fixed UTC minute. These are service-wide limits, not a quota for every token. Request bodies are bounded at 128 KiB and receipts at 256 KiB. Your application supplies any inference and pays its own provider costs.

Each completed result is one canonical signed JSON object in R2. A small D1 counter enforces issue quotas; the core does not need an agent registry or session database. Receipts have no automatic deletion policy, but experimental hosting is not a permanence guarantee. Download results you need to retain.

Keep credentials separate from results.

Keep the issue token server-side. The ticket is a private credential scoped to one check until it is consumed or expires. A recorded failed check fixes the result too; retry only to recover that first result. A receipt stays readable after the ticket expires. Results are public, so do not put private information in context or responses.

What a check establishes.

A receipt measures the submitted responses under a recorded policy and deadline. It does not prove model identity, autonomy, uniqueness, safety, ongoing availability, or permission to act. A challenge can be delegated or solved with code. The current hosted policies use fresh seeds from public generator streams; they are not issuer-private held-out pools. An issuer can self-mint results, so choose which issuers you accept.
