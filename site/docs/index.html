Make a check.

Issue fresh puzzles, submit one set of answers, and keep the signed result. Use ordinary HTTP from your own application. You supply the solver and decide how to use the evidence.

Your first receipt, with curl and jq.

The hosted API is private staging. Get an invitation token from the operator and keep it in your server environment as CLANKDAR_TOKEN. The commands below need curl and jq, and work from a fresh local directory. No agent registration or repository checkout is required.

Create a check and inspect its prompts.

export CLANKDAR_URL="https://clankdar-hosted-staging.972abc65.workers.dev"
# Set CLANKDAR_TOKEN privately to your invitation token.
umask 077
curl -fsS "$CLANKDAR_URL/v1/checks" \
  -H "Authorization: Bearer $CLANKDAR_TOKEN" \
  -H "Content-Type: application/json" \
  --data '{"policyId":"v2-floor-v1"}' > check.json
jq -r '.challenges[] | "\(.challengeId)\n\(.prompt)\n"' check.json

check.json contains the actual challenge IDs and prompts, expiresAt, and a private ticket for this check. The default v2-floor-v1 policy gives you four prompts, requires three passing answers, and allows 120 seconds. Creating the check does not call a model.

Build the answer map and submit once.

jq '.challenges | map({key: .challengeId, value: ""}) | from_entries' \
  check.json > answers.json

This creates blank answers under the real challenge IDs. Submit them unchanged for an intentionally failed-check demo. To test capability, replace each blank value with your solver’s answer before expiresAt. No model is called by these commands. Failed answers consume the attempt just as passing answers do.

jq -n --slurpfile check check.json --slurpfile answers answers.json \
  '{ticket: $check[0].ticket, responses: $answers[0]}' > submission.json
curl -fsS "$CLANKDAR_URL/v1/checks/$(jq -r '.id' check.json)/responses" \
  -H "Content-Type: application/json" \
  --data-binary @submission.json > result.json
jq '{id, pass, passed, required, receiptUrl, sha256}' result.json

The response includes pass, the passing and required counts, a content hash, a receipt URL, and the signed receipt itself. Submission uses the scoped ticket, so your main issue token stays with your server. Retrying submission recovers the first result; it cannot replace the answers. Retrying creation makes a new check and consumes another quota slot.

Download the exact JSON receipt.

curl -fsS "$CLANKDAR_URL$(jq -r '.receiptUrl' result.json)" > receipt.json

The receipt is a raw clankdar-gate-v1 signed admission with protocol, payload, and signature. It remains readable after the ticket expires. Keep a copy: this experimental service has no automatic deletion policy, but does not promise permanent hosting.

Three endpoints.

POST /v1/checks
Requires Authorization: Bearer …. Send {} for the default policy, or {"policyId":"frontier-floor-v1"}. Optional context is a nonempty, non-sensitive string up to 256 characters. The response contains id, ticket, policyId, expiresAt, challenges, and receiptUrl.
POST /v1/checks/:id/responses
Send {"ticket":"…","responses":{"actualChallengeId":"answer"}}. No issue token is needed. An empty response object is a valid failed attempt. The first accepted submission fixes the result; retries return it. You receive pass, passed, required, receiptUrl, sha256, and the signed receipt.
GET /v1/checks/:id
Returns the immutable, canonical JSON receipt after a result exists. This read needs no token. The sha256 returned on submission identifies the exact receipt bytes.

Choose a policy.

v2-floor-v1 uses the v2 pool and a 120-second deadline. frontier-floor-v1 uses harder cells and a 180-second deadline. Both ask four prompts and require three passes. These are defined task settings, not certified model classes.

Optionally bind a check to a subject key

Include subjectPublicKey when issuing a check if your application needs key binding. Submission then includes the matching subjectProof under the existing receipt protocol. A subject signature binds a key to the check; it does not prove who solved the puzzles. Most integrations can start without subject keys. See the API contract for the exact proof format.

For request bounds, retry semantics, and error responses, use the complete check API contract. A server-side JavaScript integration example connects the calls to your solve(challenges, signal) function. Forward the abort signal to provider requests. Its optional checkpoint(record) callback lets your app save the ticket and answers privately for recovery.

Verify the receipt where you use it.

Challenge receipts reveal the seeds and recorded answers for responses that were present and well-formed. A checker verifies the issuer signature, regenerates those puzzles, rescores the recorded answers, and recomputes the result. Missing or malformed answers count as nonpassing without a challenge receipt or seed reveal; the blank-answer demo still verifies as 0 of 4 passing. Copying a receipt between services does not require copying a Clankdar account or adopting a workflow.

The optional source verifier uses Bun 1.3.14 and the repository’s existing checker. Set EXPECTED_ISSUER_PUBLIC_KEY from your application’s trusted configuration, then run it from the repository:

bun cloudflare/examples/verify-receipt.mjs receipt.json \
  --issuer "$EXPECTED_ISSUER_PUBLIC_KEY" \
  --session "$(jq -r '.id' check.json)" \
  --sha256 "$(jq -r '.sha256' result.json)"

--issuer is a required signer pin. Add --context when your app requires a particular context. The verifier also checks the expected session and exact bytes when those options are supplied. See the verifier example for its output and failure behavior.

A valid signature and replay establish what the issuer recorded. Your application must also require its intended policy, appropriate freshness, and a passing result when needed. A failed check can have a completely valid receipt.

Put checks inside your workflow.

  1. Agent preflight

    When an agent offers to take a job, your service creates a check and forwards its prompts and scoped ticket. Inspect the signed result alongside your existing authentication and admission policy. Clankdar supplies evidence; your service decides whether to proceed.

  2. Release checks in CI

    Before changing a model endpoint, issue checks under the same declared policy and conditions as your baseline. Compare relevant cells and store receipt IDs with the release. Your pipeline owns sampling, thresholds, provider errors, and the release decision.

  3. Evidence on an agent listing

    Attach a recent result and receipt link to an agent in your own marketplace or directory. Show the policy, date, and sample size so readers can inspect what was tested. Decide yourself when listings need a fresh check.

Schedule your own monitoring.

Call the same endpoints from your cron job or agent loop and store the check IDs in your application. You choose cadence, budgets, missed-run treatment, and alerting. An individual check says nothing about ongoing availability. The existing campaign implementation remains an optional legacy reference; its records and routes are preserved.

The same primitive fits a one-off request or repeated evaluation. A scheduled campaign is an integration policy, not a prerequisite for calling the API.

Limits, storage, and boundaries.

Shared staging allows 1,024 issued checks over its lifetime and at most 60 issues per fixed UTC minute. These are service-wide limits, not a quota for every token. Request bodies are bounded at 128 KiB and receipts at 256 KiB. Your application supplies any inference and pays its own provider costs.

Each completed result is one canonical signed JSON object in R2. A small D1 counter enforces issue quotas; the core does not need an agent registry or session database. Receipts have no automatic deletion policy, but experimental hosting is not a permanence guarantee. Download results you need to retain.

Keep credentials separate from results.

Keep the issue token server-side. The ticket is a private credential scoped to one check until it is consumed or expires. A recorded failed check fixes the result too; retry only to recover that first result. A receipt stays readable after the ticket expires. Results are public, so do not put private information in context or responses.

What a check establishes.

A receipt measures the submitted responses under a recorded policy and deadline. It does not prove model identity, autonomy, uniqueness, safety, ongoing availability, or permission to act. A challenge can be delegated or solved with code. The current hosted policies use fresh seeds from public generator streams; they are not issuer-private held-out pools. An issuer can self-mint results, so choose which issuers you accept.

The benchmark behind the checks.

Tasks and scoring are versioned as {{SUITE_VERSION}} and {{SCORER_VERSION}}. Exact comparison preserves meaningful signs, case, token boundaries, grid dimensions, and binary leading zeroes. There is no judge model. The independent final-answer diagnostic is separate from strict pass/fail.

Compare the capability you need.

Public results are grouped by family/tier cells and profiles. The v2 calibration has 2,500 attempts from five requested model aliases, with one timeout; pooled strict scores span 9.4%–87.6%. Tiers mix different families, so they are not one intelligence number. Inspect the capability profiles, counts, exclusions, and uncertainty before choosing your own evaluation conditions.

Keep evaluation tracks separate.

Frontier measures harder unaided tasks; the tool-agent suite records bounded tool episodes. Those tracks do not share a leaderboard. Four published signed reference sessions contain 32 challenge checks, all replayed by the site build. Explore the benchmark and downloadable evidence.

Run the local benchmark from source

With Bun 1.3.14 and the repository dependencies installed:

bun bench --list
bun bench --adapter oracle --seeds 1-10 --out results/oracle-first.jsonl

oracle uses known answers to check the runner, not model capability. Model benchmark commands default to a dry run; actual inference requires --execute and a request budget. The source README covers adapters, tracks, and archives.

Public benchmark seeds and the experimental answer-commitment helper are not a strong secret-challenge or identity system. The receipt protocol specifies the commitments, signatures, and replay boundaries.
