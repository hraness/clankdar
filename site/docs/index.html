The contract, without the hand-waving

Docs.

Run the benchmark. Inspect the evidence. Keep the authority boundary separate. Clankdar ships an experimental puzzle suite and runner, plus a reference protocol stack — sealed-seed attestation, admission sessions, subject-bound receipts, a signed transparency log, and a drift monitor. A production admission service is not implemented.

Your first clank.

Use Bun 1.3.14. This repository runs directly from source; there is no published installable SDK or hosted challenge API.

git clone https://github.com/hraness/clankdar.git
cd clankdar
bun install --frozen-lockfile --ignore-scripts
bun run check
bun bench --list
bun bench --adapter oracle --seeds 1-10 --out results/oracle-first.jsonl

oracle is a privileged test control: the runner uses the known answer without calling a model. Its score checks plumbing, not model capability. echo returns the prompt and provides a simple non-solving baseline.

Inspect before spending.

bun bench --adapter openai:gpt-4o-mini --tiers 0-3 --seeds 101-110
bun bench --adapter openai:gpt-4o-mini --tiers 0-3 --seeds 101-110 \
  --execute --max-requests 200 --max-tokens 4096 --out results/model-first.jsonl

The first command only prints a manifest. The second enables API requests. Configure CLANKDAR_API_KEY privately in the environment and optionally CLANKDAR_BASE_URL; OPENAI_API_KEY and OPENAI_BASE_URL are fallbacks. Keep environment files untracked. Never paste credentials into the command line, a result file, or an issue.

--max-requests caps actual HTTP attempts, including rejected-parameter negotiation. There are no automatic retries for provider failures. --max-tokens, --timeout-ms, and --concurrency bound each run. These are request and token controls, not a guaranteed dollar cap; inspect provider pricing before opting in.

Compare the same questions across models.

CLANKDAR_BASE_URL=https://ai-gateway.vercel.sh/v1 bun calibrate \
  --models openai/gpt-4.1,google/gemini-2.5-pro --seeds 101-110

This is also a dry run. Add --execute --max-requests N --out NEW-DIRECTORY after inspecting it. Gateway model IDs use the provider’s spelling, often provider/model; the openai: prefix selects the adapter only in bun bench. Loopback HTTP endpoints support local models without an API key; remote endpoints require HTTPS.

Run the other suites.

bun bench --list
bun bench --suite frontier --adapter openai:gpt-4.1 --seeds 301-320
bun bench --suite agent --adapter agent:openai:gpt-4.1 --seeds 301-320

frontier is the deeper unaided pool: same one-response contract, harder cell parameters. agent is the bounded tool track and requires an agent-capable adapter (agent:openai:<model>); unaided adapters are refused, and agent adapters refuse unaided suites. Agent episodes make several provider requests per instance — budget --max-requests accordingly.

Correct means something precise.

The current contracts are {{SUITE_VERSION}} and {{SCORER_VERSION}}. An instance contains family, tier, seed, prompt, and answer. A model adapter receives only the first two identifiers and the prompt—not the seed or answer.

  • Text: trim and collapse whitespace; preserve case, punctuation, and token boundaries. The ALL CAPITAL LETTERS instruction really is case-sensitive.
  • Integers: accept signed decimal integers, canonicalize leading zeroes and a leading plus. Reject decimals, exponents, prose, and a wrong sign. -5 is not 5.
  • Grids: accept space-separated single-digit cells with rows separated by newlines or /. Preserve dimensions and cell boundaries; 1 2 / 3 4 is not 12 / 34.
  • Bits: preserve every digit, including leading zeroes. Ordering: parse individual letter tokens, allowing case and comma/whitespace variants. Knights: parse ordered letter-to-knight/knave assignments, not arbitrary prose.
import { familyByName, answerFormat, scoreAnswer } from "./ladder/mod.ts";

const puzzle = familyByName("arithmetic")!.generate(2, 42);
const result = scoreAnswer(puzzle.answer, response, answerFormat(puzzle.family));
result.pass;
result.finalAnswerMatch;

The final-answer diagnostic extracts a final line or block without looking at the expected answer, then applies the same typed comparison. It never changes pass. It is not substring matching, a judge-model opinion, or proof that the model understood the task.

Rule-induction tasks declare a finite hypothesis class and add examples until all surviving rules agree on the query. That is uniqueness within the stated grammar, not a claim that finite examples determine an arbitrary function.

Ask for the capability you need.

The v2 profile contract partitions all 25 cells exactly once: transform fidelity, symbolic execution, constraint solving, and rule induction. A profile score pools only its declared cells. It does not change the underlying prompts, verdicts, or family/tier results.

For evaluation, predeclare the suite hash, profile and cells, seed policy, response and tool conditions, minimum sample size, threshold, and treatment of provider errors. Prefer a lower confidence bound when a decision depends on reliability. Do not choose a threshold after seeing the candidate's answers.

Profiles describe evidence; they do not grant authority.

A service with a hard constraint-solving requirement should evaluate that profile directly instead of averaging it with easier transformations. Passing still does not establish model identity, non-delegation, safety, or permission to call tools.

The executable profile definitions and partition checks live in bench/profiles.ts. Current observed results are on the benchmark page.

The reverse CAPTCHA landscape.

A wave of “prove you’re a bot” projects appeared alongside agentic tools. Each makes a different tradeoff, and most are better understood as access gates than as capability benchmarks. A gate says the door may open; a benchmark says how well a specific system does on a reproducible task.

MoltCaptcha and similar text-constraint gates.

Challenges ask the solver to produce a coherent passage that simultaneously satisfies ASCII-sum, word-count, character-position, and total-length constraints. The AI advantage is supposedly one-shot multi-constraint planning.

What it gives you: a cheap pass/fail signal that the response was likely generated by a model rather than a human under time pressure.

What it does not give you: reproducible scores across models, calibrated difficulty, or an answer to “how capable is this agent?” A determined human can still satisfy the constraints with time or tooling.

Cryptographic and proof-of-work gates.

Signature challenges require a nonce signed with a known private key. Hashcash requires finding a nonce with leading zero bits. These prove possession or compute budget, not model capability.

What they give you: a strong “this key was here” or “this work was spent” statement.

What they do not give you: a gradient of ability. Signatures bind keys, not reasoning. Hashcash is hardware-biased and can be pooled. Neither tells you whether the agent can solve your actual problem.

Natural-language instruction challenges.

These send randomized English descriptions of byte or arithmetic transformations and require a correctly formatted proof. They test whether an agent can parse informal instructions and execute code.

What they give you: a plausible “AI, not human with curl” signal.

What they do not give you: a public, replayable record. The challenge is secret, per-session, and binary. It does not expose which model failed, how close it got, or what kind of task it failed on.

Clankdar: a programming puzzle, not a gate.

Clankdar flips the design toward model capability measurement. The task is a deterministic, seeded puzzle with a unique, re-derivable answer. The prompt is public; the answer is not sent to the model. The same seed always produces the same puzzle. The scorer is exact and typed. The results are counts, percentages, and confidence intervals on named family/tier cells.

This is a much stronger foundation for deciding “does this agent meet a capability requirement?” than any reverse CAPTCHA. It is a worse foundation for deciding “was the request sent by an AI?,” because public puzzles can be memorized or solved with code. That is a feature, not a bug: it keeps the measurement honest and the authority boundary elsewhere.

Evidence you can replay.

JSONL begins with a versioned run manifest, contains one result per instance, and ends with a summary. It records the suite hash, seed set, source revision and dirty flag, runtime, requested model and endpoint, accepted request parameters, usage where provided, finish reason, and latency. Streaming rows may arrive in completion order; instance identities and the suite hash do not depend on that order.

New files are exclusive-create: existing evidence is never truncated. Interrupted runs remain available for diagnosis, but incomplete files are rejected by the comparison report. A model timeout or provider error keeps the puzzle identity, is reported separately, and does not become a model’s wrong answer. A token-limit truncation cannot silently pass.

bun report results/my-run
bun report site/benchmark/v2-calibration-0
bun bench/archive.ts verify site/benchmark/v2-calibration-0
bun bench/pilot.ts verify site/benchmark/pilot-v0

The public v2 calibration contains 2,500 saved attempts on held-out seeds 101–120. Replaying its archive verifies hashes and recomputes every published score; calling a model again need not reproduce the same response. The report rejects mixed versions, duplicate instances, changed prompt/answer pairs, and different model coverage. The earlier pilot remains available as explicitly labeled legacy evidence.

The tool-agent track.

The agent suite runs a bounded multi-turn protocol instead of the one-response contract. Each instance carries a deterministic, server-side tool environment — the model sees the prompt and a growing transcript, never the environment internals.

TOOL <name> {json-args}    // one tool call
FINAL <answer>            // submit and end the episode

Every model reply must be exactly one action line. Anything else is a protocol error and wastes a turn. Budgets are hard per-cell caps: 4–12 tool calls, 8–16 turns, 4,096 characters per tool output. An episode ends on FINAL or with budget_exhausted. Tools are pure functions over the instance — no shell, filesystem, network, or secrets.

Transcripts are recorded per attempt and replayed against regenerated environments on verification, so a published score is backed by deterministic tool execution, not a claimed one. The agent manifest records the protocol version (clankdar-agent-protocol-v1) alongside the usual run metadata.

On the benchmark page, the episode-diagnostics table adds four more signals:

  • FINAL emitted — how often the model ended the episode by actually submitting an answer rather than hitting the turn cap.
  • Budget exhausted — episodes that never emitted FINAL. The scorer still grades the last reply text, so a bare answer on the final turn can pass; in practice these almost never satisfy the contract.
  • Mean tool calls / turns — effort under the recorded budget. A cheap solve reads differently from an expensive one.
  • Failed tool calls — protocol violations, unknown tools, invalid arguments, and call-budget hits, split by kind.
Agent scores are not unaided scores.

They measure planning and tool use under one declared contract and budget. Do not compare them to unaided runs, and do not treat a passed agent episode as evidence of real-world tool access or safe behavior — the environments are synthetic and replayable by design.

The admission exchange.

clankdar-attest-v1 is the implemented wire format. A verifier commits to a fresh unrevealed seed and publishes the generated prompt, so the instance cannot be pre-solved or looked up. A response inside the deadline is rescored deterministically and signed into a receipt that reveals the seed — anyone replays the signature, the commitment, the regenerated instance, and the verdict without trusting the issuer. clankdar-gate-v1 builds admission sessions on top: a policy draws N sealed challenges under one session id and one deadline, and one submit consumes the session into a signed admission whose verdict recomputes independently. clankdar-tlog-v1 derives a transparency log from the gate ledger: every session and decision becomes a hash-chained entry under an issuer-signed head, so issued events are enumerable and replayable. The specification is docs/clankdar-attest-v1.md.

bun bench/attest.ts keygen --out verifier.json
bun bench/gate.ts policy --suite frontier \
  --cells automata:t6,knights:t5,registervm:t5 \
  --challenges 3 --min-pass 2 --ttl 300 --out policy.json
bun bench/gate.ts serve --key verifier.json \
  --policy policy.json --dir gate-state --port 8787
POST /sessions                → {sessionId, expiresAt, challenges[]}
POST /sessions/:id/responses  → {admission, receipts[]}
GET  /receipts/:challengeId   → one independently replayable receipt
GET  /policy                  → the floor and the verifier key
bun bench/tlog.ts build --dir gate-state --key verifier.json --out tlog.json
bun bench/tlog.ts check tlog.json                     → recompute the chain and head signature
bun bench/tlog.ts prove tlog.json --session gs_…      → inclusion evidence for one session
bun bench/tlog.ts admit tlog.json admission.json      → admission check + logged history

The log binds this issuer's history under its own key. It does not stop self-minting — a verifier can always answer its own oracle — and it cannot detect a fork alone: equivocation is visible only by comparing heads the issuer published elsewhere, and gossip, witnessed co-signing, and external anchoring are not implemented. What the log buys is enumerability: an admission that does not trace to a logged session is issuer-claimed only.

An admission attests that one session produced K passing responses under one policy in one window. It is capability evidence — never identity, liveness, or authority — and arbitrary model or room text must never issue authority. reference implemented

Subject binding.

A respondent can attach a subjectProof: an Ed25519 signature by a key it controls over a domain-separated transcript. One proof covers a whole gate session — ["clankdar/subject/v1", sessionId, publicKey] — and embeds in every minted receipt; a standalone challenge binds challengeId, nonce, and key instead. The issuer validates the proof at minting (an invalid one is a minting error, never a receipt field), and an admission carries at most one subject key across all its receipts.

What it buys: one pseudonymous subject key can sign across receipts, sessions, and verifiers — the binding that portable capability badges and receipt-chaining need. What it does not buy: the key holder can still delegate the solving and sign afterward, so a proof says who claimed the episode, not who solved it; it carries no liveness, expiry, or revocation of its own. Badge aggregation and a portable badge format are not implemented — this is the binding they would build on.

The drift monitor.

bun drift points the same gate machinery at your own model endpoint on a schedule. Every round is a real signed admission appended to a series file — the series is evidence, not telemetry.

bun drift run --key verifier.json --policy policy.json \
  --adapter openai:gpt-4.1 --rounds 5 --series drift.jsonl \
  --execute --max-requests 100
bun drift report --series drift.jsonl
bun drift baseline --series drift.jsonl --out baseline.json
bun drift compare --series drift.jsonl --baseline baseline.json --threshold 0.2

report aggregates per-cell and overall pass bands; baseline pins a reference series; compare exits nonzero when a cell or the overall band drops more than --threshold below the pin — a CI gate for silent model substitution. Score bands describe the probed endpoint under the recorded policy; they are not a certification of the provider.

Modes.

Hashcash

The small anti-spam primitive. A response meets a SHA-256 leading-zero target over a bound challenge and nonce. Cheap to verify, hardware-biased, and outsourceable; it does not establish exact resource spend or model capability. Signed challenge and replay-guard code lives in the Rust prototype. prototype

Witness

A bounded deterministic program can be replayed with a work receipt. The standalone Rust witness VM exists; integrating it with signed admission challenges remains design work. Charged operations are a defined VM contract, not evidence of the solver’s identity or physical energy use. standalone prototype

Ladder

The benchmark generators, exact scorer, runner, verifier-keyed answer commitment, sealed-seed attestation (attest-v1), admission sessions (gate-v1), the issuance transparency log (tlog-v1), and the drift monitor are implemented here — signed issuance, seeded challenge commitments, policy floors, subject-bound receipts, session binding, a durable append-only consumption ledger, and a derived signed log over it. A hosted issuer, log gossip or anchoring, rate limits, held-out pools, and portable badge aggregation are not. The current public-seed suite must not be used as a secret admission generator. reference implemented

Verification.

The gate verifier and the independent admission checker enforce:

  1. strictly parse and bound every field;
  2. verify the issuer signature and protocol version over the recorded payload bytes;
  3. require the declared subject, context, session, suite version, and policy cells;
  4. reject expired challenges and already-decided sessions;
  5. regenerate each instance from its committed seed and rescore every embedded receipt — claimed work is never trusted;
  6. verify any embedded subjectProof over its domain-separated transcript and require one subject key per session;
  7. recompute the verdict against the policy's challenge count and minimum-pass threshold; and
  8. consume each session once, atomically, for the declared admission purpose.

Binding and replay.

  • challenge_id is cryptographically random and unpredictable until issuance; a session's challenges share one session_id and one deadline.
  • The seed commitment binds suite version, family, tier, nonce, and seed in a domain-separated digest, preventing cross-session and cross-purpose reuse; the signature binds the rest of the transcript.
  • The gate ledger consumes each session once: receipts and the signed admission append as a single record. Duplicate submits are rejected; a restart cannot resurrect an undecided session.
  • An optional subjectProof binds each receipt to a respondent Ed25519 key through a clankdar/subject/v1 transcript scoped to the session — or to the standalone challenge's id and nonce. The domain label keeps a proof from being reinterpreted as any other protocol message.
  • The transparency log hash-chains every ledger record — each entry's prev links to the prior entryHash under an issuer-signed head — so a dropped, reordered, or altered record breaks verification. A fork is detectable only by comparing heads the issuer published elsewhere.
  • Replay consumption is atomic and durable across restarts. An in-memory guard alone is not a production admission ledger.

Security model.

No software-only challenge can prove that a human, an LLM, or an autonomous agent produced the answer. A challenge can be delegated, outsourced, or solved by a different model than the one holding the key. Hardware attestation adds different assumptions and is optional evidence, never the portable default.

A successful response may remove a rate limit or qualify admission. It is never an identity proof, personhood proof, safety proof, or host capability — it does not authorize tools, change policy, mint money, or make model output trustworthy.

A subject proof does not relax the delegation limit: the key holder can relay the challenge to a stronger solver and sign the transcript afterward. The verifier can also answer its own oracle — the transparency log makes one issuer's history enumerable but cannot detect a fork alone, so relying parties should issue their own challenges and treat foreign admissions as issuer-claimed.

The answer-commitment boundary.

A public hash of a small answer space is an offline guessing oracle. A random public salt does not fix that. The experimental helper therefore requires a verifier-secret key of 32–64 bytes and uses HMAC-SHA256 over an unambiguous, versioned transcript:

HMAC-SHA256(verifier_key, JSON.stringify([
  "clankdar/answer/v2\0",
  "{{SCORER_VERSION}}",
  challenge_id,
  answer_format,
  canonical_answer
]))

answerCommitment(challengeId, answer, verifierKey, format) produces the tag. verifyAnswer(challengeId, tag, response, verifierKey, format) rejects malformed answers and compares fixed-length tags in constant time. V1 unkeyed commitments are intentionally not accepted.

  • Keep the key server-side. This is not a public-verification proof. Publishing the key defeats the protection.
  • Bind the rest of the protocol separately. The helper does not sign a challenge, bind a subject or scope, enforce expiration, or consume replay state. A signed envelope must bind the prompt hash, family, tier, scoring version, identity, purpose, and lifetime.
  • Benchmark entropy is not admission entropy. The suite uses a 32-bit, non-cryptographic Mulberry32 RNG. Hiding that seed is insufficient. Fresh admission needs a separately designed, cryptographically generated challenge system.
  • Limit online guesses and delegation. Even keyed commitments do not increase answer entropy, stop outsourcing, or prove that a named model supplied the answer.
